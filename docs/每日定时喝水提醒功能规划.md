## 1. 背景与目标

### 1.1 背景

人体每天约需补充 1500–2000 ml 水分，但大多数人在专注工作、开会、通勤时会忘记喝水，导致：
- 长期轻度脱水，引发疲劳、头痛、注意力下降；
- 一次性大量饮水，加重肾脏与心脏负担；
- 到晚间才补水，影响睡眠质量。

现有提醒工具多为“固定闹钟”，存在两个痛点：**提醒时间僵硬**（无论用户作息如何都按固定点响）和 **缺乏记录与反馈**（用户看不到自己的饮水完成度）。

### 1.2 目标

| 目标类型 | 描述 | 衡量方式 |
|---------|------|---------|
| 产品目标 | 用“自适应时间表 + 轻量记录”帮助用户达成每日饮水目标 | 日均达标用户占比 |
| 用户目标 | 无需手动设置，也能在合适的时间收到恰到好处的提醒 | 提醒接受率、关闭率 |
| 技术目标 | 提醒准时、跨天状态正确、低打扰、可离线降级 | 到达率、异常率 |

### 1.3 非目标（本期不做）

- 不做硬件联动（智能水杯、传感器）——预留接口即可；
- 不做医学级饮水建议与疾病相关提示；
- 不做社交排行、打卡分享等玩法；
- 不采集用户身体数据（体重/病史）以外的隐私信息。

## 4. 交互与提醒策略

### 4.1 时间表生成算法

输入：
- `active_start` / `active_end`：活跃时段（如 09:00–21:00）
- `target_ml`：每日目标（默认 1800 ml）
- `per_ml`：单次饮水量（默认 250 ml）
- `min_gap` / `max_gap`：提醒间隔上下限（默认 45 / 120 分钟）
- `quiet_ranges`：免打扰区间列表

输出：当日 `reminder_times` 列表。

```python
from datetime import datetime, timedelta

def build_schedule(active_start: datetime, active_end: datetime,
                   target_ml: int = 1800, per_ml: int = 250,
                   min_gap: int = 45, max_gap: int = 120,
                   quiet_ranges: list[tuple[datetime, datetime]] = None) -> list[datetime]:
    """生成当日提醒时刻表。

    在活跃时段内均匀分布 count 个提醒，剔除落入免打扰区间的时刻（跳过不补）。
    """
    quiet_ranges = quiet_ranges or []
    total_minutes = int((active_end - active_start).total_seconds() // 60)
    count = max(1, round(target_ml / per_ml))
    # 均匀间隔，夹到 [min_gap, max_gap] 之间，并取整到分钟
    gap = round(min(max(total_minutes / count, min_gap), max_gap))

    times, cursor = [], active_start
    while cursor <= active_end and len(times) < count:
        if not any(qs <= cursor < qe for qs, qe in quiet_ranges):
            times.append(cursor)
        cursor += timedelta(minutes=gap)
    return times
```

说明：`count = target_ml / per_ml`（如 1800/250 ≈ 7 次），间隔按活跃时长均分后再夹到上下限，避免“过于密集”或“过于稀疏”；`gap` 取整到分钟，避免出现 `10:42:51` 这类带秒零头的提醒时刻。

被静默剔除的时刻**不会立即停止推进**：循环继续按固定 `gap` 前进，只要活跃时段还有余量就会补齐次数；余量不足时，当日实际次数少于目标（对应 E2）。

### 4.2 提醒文案

| 场景 | 文案示例 |
|------|---------|
| 常规提醒 | 该喝水啦 💧 今天已完成 3/7 |
| 距目标较远 | 还差 750ml，来一杯吧 |
| 收官提醒 | 最后一杯，今天达标啦 |
| 已达目标 | 今日目标已达成，可自由补水 |
| 静默期结束 | （不补发，次日正常） |

### 4.3 通知操作按钮

| 按钮 | 行为 |
|------|------|
| 已喝 | 记录 `per_ml`，更新进度 |
| 稍后 | 延后一个 `min_gap` 重提醒（最多 2 次） |
| 跳过 | 丢弃本次，不计入完成 |

### 4.4 状态机

```
IDLE ──开启/到达活跃时段──▶ ACTIVE
ACTIVE ──用户点“今天不再提醒”──▶ SKIPPED_TODAY ──次日 00:00──▶ IDLE
ACTIVE ──进入免打扰区间──▶ PAUSED ──离开区间──▶ ACTIVE
ACTIVE/SKIPPED_TODAY ──关闭总开关──▶ IDLE
```

- **跨天重置**：按本地日历日 00:00 重置，而非 24 小时计时，规避时区与夏令时问题。
- **免打扰**：静默期内的提醒**直接丢弃**，不顺延，避免静默结束后连响多次。

## 5. 一周计划（Week Plan）

### 5.1 为什么需要一周计划

4.1 的算法默认「每天参数相同」，但真实的一周是**不均匀**的：工作日 9 点已经在工位，周末 10 点可能还没起床；周三是固定训练日，需要多补 200 ml；周五晚上有饭局，不必再提醒。若只支持一套参数，用户会遇到两类问题：

- **周末被过早打扰** → 干脆关掉总开关，周一到周五也一起失去提醒；
- **运动日摄入不足** → 目标水量按普通工作日算，训练日长期补水不够。

因此引入**周计划模板**：把「一周 7 天各自的参数」作为持久配置，每日时间表由当日生效参数派生。周计划是**参数层**，日时间表是**结果层**，两者分离。

### 5.2 数据结构与解析优先级

```python
from dataclasses import dataclass, field, replace
from datetime import date, datetime

@dataclass
class DayPlan:
    """一周中某一天的独立参数（字段含义同 WaterSettings）。"""
    weekday: int                              # 0=周一 … 6=周日
    active_start: str = "09:00"
    active_end: str = "21:00"
    target_ml: int = 1800
    per_ml: int = 250
    quiet_ranges: list[tuple[str, str]] = field(default_factory=lambda: [("12:30", "13:30")])
    enabled: bool = True                      # 该天是否提醒（如「周日全天休息」）

@dataclass
class WeekPlan:
    days: list[DayPlan]                       # 长度固定 7，索引即 weekday
    updated_at: datetime

@dataclass
class DayOverride:
    """当日临时覆盖：只影响指定那一天，次日失效。"""
    day: date
    patch: dict                               # 仅覆盖显式给出的字段

def resolve_day_plan(week: WeekPlan, day: date, override: DayOverride | None) -> DayPlan:
    """周模板 + 当日覆盖 → 当日生效参数。

    优先级：当日覆盖 > 周模板；任一层都未指定时用 DayPlan 默认值。
    """
    base = week.days[day.weekday()]
    if override and override.day == day:
        return replace(base, **override.patch)
    return base
```

**解析优先级（从高到低）**

| 优先级 | 层级 | 作用范围 | 生命周期 |
|--------|------|---------|---------|
| 1 | 当日覆盖 `DayOverride` | 仅当天 | 到次日 00:00 自动失效 |
| 2 | 「今天不再提醒」SKIPPED_TODAY | 仅当天 | 到次日 00:00 自动失效 |
| 3 | 周计划模板 `WeekPlan` | 每周循环 | 持久保存，直到用户修改 |
| 4 | 全局默认值 | 兜底 | 代码内置 |

> 与 4.4 状态机的关系：SKIPPED_TODAY 会让当天所有提醒失效，优先级高于周模板；但**不修改**周模板，次日仍按原计划恢复。

### 5.3 默认一周模板

下表的「次数」= `round(target_ml / per_ml)`，间隔由 (活跃时长 / 次数) 均分后再夹到 `[45, 120]` 分钟并取整到分钟（算法见 4.1）。表中数值已用 4.1 / 5.4 代码实跑校验。

| 星期 | 活跃时段 | 目标水量 | 单次 | 次数 | 实际间隔 | 免打扰 | 备注 |
|------|---------|---------|------|------|---------|--------|------|
| 周一 | 09:00–21:00 | 1800 ml | 250 ml | 7 | 103 min | 12:30–13:30 | 常规工作日 |
| 周二 | 09:00–21:00 | 1800 ml | 250 ml | 7 | 103 min | 12:30–13:30 | 常规工作日 |
| 周三 | 09:00–21:30 | 2000 ml | 250 ml | 8 | 94 min | 12:30–13:30 | **运动日**，目标上调 |
| 周四 | 09:00–21:00 | 1800 ml | 250 ml | 7 | 103 min | 12:30–13:30 | 常规工作日 |
| 周五 | 09:00–21:00 | 1800 ml | 250 ml | 7 | 103 min | 12:30–13:30 | 常规工作日（周末前夜） |
| 周六 | 10:00–22:00 | 1800 ml | 300 ml | 6 | 120 min | 13:00–14:00 | **周末**：晚起、单次加大 |
| 周日 | 10:00–21:00 | 1600 ml | 300 ml | 5 | 120 min（夹上限后） | — | **休息日**：目标略降 |

实跑结果（以 2026-10-12 周一为起点）：

```
周一 09:00 10:43 12:26 14:09 15:52 17:35 19:18
周三 09:00 10:34 12:08 13:42 15:16 16:50 18:24 19:58
周六 10:00 12:00 14:00 16:00 18:00 20:00
周日 10:00 12:00 14:00 16:00 18:00
一周合计 47 条通知
```

模板仅为**初始值**，首次开启时写入 `WeekPlan`，之后完全由用户配置驱动；支持三种预设一键套用：

- **工作日预设** → 工作日 09:00–21:00 / 1800 ml / 250 ml / 午休静默；
- **周末预设** → 10:00–22:00 / 1800 ml / 300 ml / 午睡静默；
- **运动日预设** → 目标 +200 ml、间隔下限收紧到 30 min、训练后 1 小时内加密提醒。

> 边界语义提醒：静默判定为左闭右开（`start <= t < end`）。以上表周六为例，间隔 120 min 时落在 14:00 的提醒**不会被** 13:00–14:00 的静默吃掉（14:00 不满足 `< 14:00`），因此周六仍是完整 6 次。
>
> 静默剔除后的补位行为：若把周五活跃时段延长到 09:00–21:30 而目标仍为 7 次，间隔变为 107 min，12:34 的提醒落入午休被丢弃，循环继续推进补齐次数，末条落在 21:29——**能补则补，补不下就少一次**（E2）。

### 5.4 一周时间表生成与滚动窗口

```python
from datetime import date, datetime, time, timedelta

def build_week_schedule(week: WeekPlan, start_date: date,
                        override: DayOverride | None = None) -> dict[date, list[datetime]]:
    """生成 start_date 起连续 7 天的提醒时刻表（键为日期，值为当日时刻列表）。"""
    result: dict[date, list[datetime]] = {}
    for i in range(7):
        day = start_date + timedelta(days=i)
        plan = resolve_day_plan(week, day, override)
        if not plan.enabled:
            result[day] = []                    # 该天关闭：显式空列表，区别于「未排程」
            continue
        to_dt = lambda s: datetime.combine(day, time.fromisoformat(s))
        result[day] = build_schedule(          # 复用 4.1 的日算法
            to_dt(plan.active_start), to_dt(plan.active_end),
            target_ml=plan.target_ml, per_ml=plan.per_ml,
            quiet_ranges=[(to_dt(a), to_dt(b)) for a, b in plan.quiet_ranges],
        )
    return result
```

**滚动窗口策略**：不一次性把 7 天全部注册到系统通知，而是

1. 首次排程注册**未来 2 天**（约 13–15 条通知）；
2. 每天本地时间 00:00 触发 `on_day_change()`，把窗口向后滚动一天，补齐第 3 天；
3. 用户修改周计划 / 设置当日覆盖 / 切换时区时，**立即重算并全量替换**窗口内通知。

原因：iOS 对单个 App 的待定本地通知数量有上限（64 条），若按 7 天全量注册（默认模板约 47 条）再叠加「稍后提醒」追加的通知，容易触顶导致**静默丢提醒**；2 天窗口 + 每日滚动既留出安全余量，也能保证改配置后快速生效。

### 5.5 交互设计

| 入口 | 能力 |
|------|------|
| 设置 → 一周计划 | 7 行列表（星期一~日），每行显示时段、目标、次数、是否开启；点行进编辑 |
| 一键预设 | 「套用工作日模板」「套用周末模板」「套用运动日模板」，可多选星期后批量套用 |
| 复制到其他天 | 编辑某天后可「复制到…」，多选目标星期，避免逐天重复配置 |
| 单日开关 | 某行可整体关闭（`enabled=false`），当天不提醒，列表置灰显示 |
| 今日临时调整 | 首页「今天特殊」→ 调整时段/目标，生成 `DayOverride`，页面标注「今日临时调整，明日恢复」 |
| 周计划总览 | 展示本周每日计划提醒次数与今日进度，一眼看出哪天配置异常（如次数为 0） |

交互约束：

- 保存周计划需**二次确认**（影响未来所有同星期日期），并提供「撤销」；
- 编辑某天时若改动会与现有当日覆盖冲突，提示「今日已有人工调整，是否覆盖？」；
- 修改某一天默认**不影响**其他天，避免「改周一顺手改掉整周」。

## 6. 技术方案

### 6.1 分层架构

```
┌───────────────────────────────────────┐
│ 表现层   首页进度 / 设置页 / 通知回调   │
├───────────────────────────────────────┤
│ 业务层   时间表生成 / 记录 / 状态机     │
├───────────────────────────────────────┤
│ 调度层  本地定时器 + 系统通知 API        │
├───────────────────────────────────────┤
│ 数据层  本地存储(默认) / 云同步(可选)   │
├───────────────────────────────────────┤
│ 平台层  iOS Notification / Android AlarmManager │
└───────────────────────────────────────┘
```

### 6.2 数据模型

```python
from dataclasses import dataclass, field
from datetime import date, datetime

@dataclass
class WaterSettings:
    enabled: bool = True
    active_start: str = "09:00"
    active_end: str = "21:00"
    target_ml: int = 1800
    per_ml: int = 250
    min_gap: int = 45
    max_gap: int = 120
    quiet_ranges: list[tuple[str, str]] = field(default_factory=lambda: [("12:30", "13:30")])

@dataclass
class DailyRecord:
    day: date
    consumed_ml: int = 0
    entries: list[tuple[datetime, int]] = field(default_factory=list)

@dataclass
class ReminderState:
    state: str = "IDLE"          # IDLE / ACTIVE / PAUSED / SKIPPED_TODAY
    next_fire_at: datetime | None = None
```

> 周计划相关数据模型（`DayPlan` / `WeekPlan` / `DayOverride`）见 5.2；`WaterSettings` 作为全局兜底默认值保留。

### 6.3 核心接口

| 接口 | 签名 | 说明 |
|------|------|------|
| 生成时间表 | `build_schedule(settings) -> list[datetime]` | 纯函数，可单测 |
| 解析当日参数 | `resolve_day_plan(week, day, override) -> DayPlan` | 周模板 + 当日覆盖，纯函数可单测 |
| 生成一周时间表 | `build_week_schedule(week, start_date) -> dict[date, list[datetime]]` | 连续 7 天，逐日复用 `build_schedule` |
| 保存周计划 | `save_week_plan(week) -> None` | 落库后全量替换滚动窗口内通知 |
| 设置当日覆盖 | `set_day_override(patch) -> DayOverride` | 仅当天生效，次日 00:00 清理 |
| 记录饮水 | `log_intake(ml) -> DailyRecord` | 幂等：同按钮重复点击不重复计数 |
| 查询进度 | `get_progress(day) -> Progress` | 返回已喝/目标/百分比 |
| 切换静默 | `skip_today() -> None` | 置 SKIPPED_TODAY，次日重置 |
| 调度注册 | `schedule_all(times) -> None` | 与系统通知绑定 |
| 跨天重置 | `on_day_change() -> None` | 由系统日历事件触发 |

### 6.4 关键技术点

| 关键点 | 方案 |
|--------|------|
| **幂等** | 通知按钮与 App 内记录共用同一 `log_id`，重复调用只生效一次 |
| **跨天** | 监听本地日期变更事件，00:00 重置，不使用 24h 计时 |
| **时区** | 全部使用用户本地时区；旅行改时区时重算当日剩余时刻 |
| **权限降级** | 通知权限被拒 → 站内横幅提醒；后台受限 → 使用系统级定时 API |
| **省电** | 用系统调度（iOS UNCalendarNotificationTrigger / Android AlarmManager）而非常驻后台进程 |

## 7. 边界与异常

| 编号 | 场景 | 处理 |
|------|------|------|
| E1 | 目标水量小于单次水量 | 至少生成 1 次提醒，并在设置页提示 |
| E2 | 活跃时段短于最小间隔 | 按 `min_gap` 压缩，允许提醒次数少于目标 |
| E3 | 免打扰覆盖整个活跃时段 | 当日不提醒，设置页给出冲突提示 |
| E4 | 用户手动改系统时间 | 以新的本地时间为准，重算剩余时刻 |
| E5 | 通知权限被拒绝 | 降级为站内提醒 + 设置页引导 |
| E6 | App 被杀死 | 依赖系统级定时通知，不依赖进程存活 |
| E7 | 跨天时用户仍在活跃时段（如通宵） | 00:00 重置计数，新一天重新排程 |
| E8 | 周计划中某天整体关闭（`enabled=false`） | 该天不注册任何通知，列表置灰并标注「本日不提醒」 |
| E9 | 用户在某天编辑周计划，影响当日已在运行的时间表 | 立即停止当日未触发的旧通知、按新参数重排，已过时刻不补发 |
| E10 | 当日覆盖与周模板冲突 | 以当日覆盖为准，UI 标注「已临时调整」；次日 00:00 自动回落周模板 |
| E11 | 一周内跨越时区变更（出差/旅行） | 按本地日期重新解析当天 DayPlan，并重算窗口内全部剩余时刻 |
| E12 | 周计划保存后与「今天不再提醒」叠加 | SKIPPED_TODAY 优先，当日静默；周模板不改动，次日恢复 |

## 8. 指标与埋点

### 8.1 北极星指标

**每日达标用户占比（DAU 中完成度 ≥ 100% 的比例）**

### 8.2 关键指标

| 指标 | 定义 |
|------|------|
| 提醒到达率 | 实际弹出次数 / 计划提醒次数 |
| 提醒响应率 | 点击“已喝”的比例 |
| 记录转化率 | 有记录的用户 / 收到提醒的用户 |
| 功能留存 | 开启提醒后第 7 天仍在用的比例 |
| 静默率 | 触发“今天不再提醒”的比例 |
| 周计划使用率 | 编辑或套用周计划的开启用户占比（衡量差异化配置的真实需求度） |
| 周末准时率 | 周末首条提醒出现在用户设定活跃时段内的比例（验证「周末不被早打扰」） |

### 8.3 埋点事件

| 事件名 | 触发时机 | 关键参数 |
|--------|---------|---------|
| `reminder_scheduled` | 生成时间表 | count, target_ml |

| `reminder_action` | 用户点击按钮 | action(drink/snooze/skip) |
| `intake_logged` | 记录成功 | ml, source |
| `daily_goal_reached` | 当日达标 | elapsed_min |
| `week_plan_saved` | 保存/套用周计划 | preset, changed_weekdays, day_count |
| `day_override_set` | 设置今日临时调整 | fields, source(today_card/settings) |
| `week_reminder_scheduled` | 生成一周时间表 | week_start, total_count, window_days |

- iOS / Android 后台与杀进程场景下的定时准确性；
- 免打扰区间边缘（正好落在边界时刻）。

### 9.4 验收清单

- [ ] 活跃时段内按目标次数均匀提醒，误差 ≤ 1 分钟

- [ ] 免打扰区间内无任何提醒
- [ ] 点“今天不再提醒”后当日静默，次日自动恢复

- [ ] 周计划中关闭的某天全天无提醒，且不影响其他天
- [ ] 修改周计划后，窗口内已注册的旧通知被正确替换，无重复弹出

## 11. 风险

| 风险 | 影响 | 应对 |
|------|------|------|
| 系统后台限制导致提醒不准时 | 到达率下降 | 使用系统级定时 API + 到达率监控 |
| 提醒过于频繁引发反感 | 关闭率上升 | 频率上下限 + 自适应调整 + 一键静默 |
| 跨时区/夏令时边界出错 | 状态错乱 | 统一按本地日历日重置 + 边界测试 |
| 用户不记录导致数据缺失 | 指标失真 | 通知按钮直记，降低操作成本 |
| 周计划配置项过多导致放弃配置 | 差异化能力形同虚设 | 提供三套预设 + 一键复制到其他天，默认模板开箱可用 |
| 待定通知数量触顶被系统丢弃 | 静默漏提醒 | 只注册未来 2 天 + 每日滚动补充，改配置后全量替换 |
